# Agent 开发闭环

这个流程用来避免 agent 在已有项目里乱改、改大、改完无法判断对错。

核心句：

```text
读代码 → 定范围 → 写验收 → 小步改 → 跑检查 → 汇报风险
```

## 以后怎么用

不用每次复制完整流程。开任务时直接说：

```text
按 agent 开发闭环处理这个任务：

任务：

约束：

我希望最后能验证：
```

如果是在当前项目里长期开发，可以把这句话升级成项目规则：

```text
之后涉及代码修改的任务，默认按 agent 开发闭环执行：
先读代码和确认范围，再写验收标准，再小步实现，最后运行检查并汇报风险。
```

## Agent 必须先做的事

在改代码前，agent 应该先回答：

1. 这个任务涉及哪些页面、接口、数据或文件。
2. 当前实现大概是怎么工作的。
3. 准备修改哪些文件，为什么。
4. 哪些地方不应该改。
5. 完成后怎么验证对错。

## 任务闸门

### 1. 读代码

先理解现状，不急着改。

适合对 agent 说：

```text
先不要改代码。请阅读相关文件，说明当前流程、入口、数据流和风险点。
```

### 2. 定范围

把改动压小。

适合对 agent 说：

```text
请提出最小改动方案，列出要改的文件和不改的范围。暂时不要写代码。
```

### 3. 写验收

把“感觉完成”变成可检查行为。

适合对 agent 说：

```text
实现前先列验收标准。验收标准要能通过页面操作、测试或数据结果判断。
```

### 4. 小步改

一次只改一层，不同时改太多东西。

优先顺序：

1. 数据结构
2. 后端逻辑
3. 前端页面
4. 权限控制
5. 汇总统计
6. 报告展示

### 5. 跑检查

让 agent 自己先发现问题。

适合对 agent 说：

```text
改完后请运行可用的测试、类型检查或启动检查。如果没有自动测试，请给我最小手动验证步骤。
```

### 6. 汇报风险

最后不要只说“完成了”。

agent 应该汇报：

1. 改了什么。
2. 没改什么。
3. 验证了什么。
4. 哪些地方还没验证。
5. 下一步建议。

## 360 环评项目里的例子

不要这样派任务：

```text
帮我做提交评价功能。
```

更好的说法：

```text
按 agent 开发闭环处理这个任务：

任务：实现评价提交时的必填校验。

约束：
- 先不要改数据库结构
- 不改页面视觉样式
- 不改管理员统计逻辑

我希望最后能验证：
- 未填写必填题时不能提交
- 填完必填题后可以提交
- 提交失败时页面有明确提示
- 提交成功后刷新不会重复提交
```

## 判断 agent 有没有跑偏

如果出现这些情况，要让它停下来重新定范围：

- 一次改了很多无关文件。
- 没有解释为什么改这些文件。
- 没有验收标准。
- 改完只说“完成”，没有运行检查。
- 为了修一个小问题顺手重构大块代码。
- UI、数据、权限、统计同时大改。
